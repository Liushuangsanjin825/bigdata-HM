# H&M 个性化推荐系统项目历程报告

## 1. 项目概述

本项目基于 Kaggle `H&M Personalized Fashion Recommendations` 数据集，目标是根据用户历史交易、用户画像和商品元数据，为每位顾客预测未来 7 天最可能购买的 12 件商品。项目使用官方指标 `MAP@12` 评估推荐结果，核心难点在于用户和商品规模较大，不能直接对全量用户-商品组合建模，需要采用“候选召回 + 排序重排”的两阶段推荐系统架构。

项目数据规模如下：

| 数据表 | 规模 | 作用 |
|:---|---:|:---|
| `transactions_train.csv` | 31,788,324 条交易 | 用户历史购买行为 |
| `customers.csv` | 1,371,980 个用户 | 年龄、会员状态、新闻订阅等用户画像 |
| `articles.csv` | 105,542 个商品 | 商品类型、品类、颜色、部门等元数据 |
| `sample_submission.csv` | 1,371,980 个用户 | 需要覆盖的全量提交用户 |

截至 2026-06-17，项目已经从早期 EDA 和规则 Baseline 推进到包含多源召回、LightGBM Classifier/Ranker、Optuna 调参、时间验证、消融分析、内存优化和提交融合的完整推荐系统。当前阶段性最佳 Kaggle 线上成绩为 Private `0.02881` / Public `0.02875`。

## 2. 第一阶段：数据理解与 EDA

项目最初从课程大作业的数据分析要求出发，首先完成了对 H&M 数据集的结构梳理、数据质量检查和业务规律分析。早期工作重点包括：

1. 明确官方提交格式：每个 `customer_id` 输出最多 12 个 `article_id`，并覆盖 sample submission 中全部用户。
2. 明确评价指标：`MAP@12` 不只关注是否命中，还关注命中商品在推荐列表中的排序位置。
3. 分析交易时间趋势：H&M 商品购买受季节和近期流行趋势影响明显，近 7 天、近 30 天热度对未来一周预测更有价值。
4. 分析用户行为差异：活跃用户可依赖近期历史行为，低活跃用户和无历史用户需要使用热门和画像兜底。
5. 分析商品属性分布：`product_type`、`garment_group`、`department` 等属性有明显业务含义，但过细属性可能引入噪声。

这一阶段形成了后续建模的基本判断：H&M 推荐任务不是简单推荐全局热门商品，而是要在用户历史偏好、近期趋势、商品属性和冷启动兜底之间取得平衡。

## 3. 第二阶段：规则 Baseline 与工程闭环

在完成 EDA 后，项目首先实现规则推荐 Baseline，目标是先打通端到端工程流程，而不是一开始追求复杂模型。

早期规则 Baseline 的主要召回来源包括：

- 用户近期历史购买商品
- 用户长期历史购买商品
- 渠道热门商品
- 部门热门商品
- 年龄段热门商品
- 近期趋势热门商品
- 全局热门商品兜底

该阶段完成了从原始数据读取、规则推荐生成、Top12 去重补齐、提交文件生成到格式校验的完整闭环，并能够稳定输出 `outputs/submission.csv`。

早期规则 Baseline 的代表性结果：

| 模型阶段 | Local MAP@12 | Public | Private |
|:---|---:|---:|---:|
| 规则融合 Baseline | 0.020806 | 0.01828 | 0.01841 |

这一阶段的意义在于为后续所有实验建立了可比较的基准，也确保项目不只是分析报告，而是能够真正生成 Kaggle 可提交结果。

## 4. 第三阶段：时间窗口验证体系

推荐系统预测的是未来行为，因此不能使用随机划分验证集。随机划分会导致训练集中出现验证窗口之后的交易记录，形成数据穿越，使本地分数虚高。

项目采用时间窗口验证方式：

1. 使用某个日期之前的交易作为历史特征期。
2. 使用之后 7 天的真实购买作为验证标签。
3. 按用户生成候选商品并计算 `MAP@12`。
4. 对不同时间窗口重复验证，以观察模型稳定性。

这一阶段将项目从“能跑代码”推进到“能正确评估模型”。后续所有候选召回、特征工程、模型参数和融合策略，都以时间窗口验证和 Kaggle 线上反馈共同判断是否保留。

## 5. 第四阶段：生成层与评估层解耦

随着规则调参和 Kaggle 提交次数增加，项目对代码结构进行了拆分：

| 文件 | 职责 |
|:---|:---|
| `Final_Project.py` | 规则 Baseline 与提交文件生成 |
| `Final_Project_Eval.py` | 规则权重调参与离线时间验证 |
| `Final_Project_LGBM.py` | LightGBM 候选排序增强流水线 |
| `LGBM_Ablation_SHAP_Analysis.py/ipynb` | 消融实验与 SHAP 可解释性分析 |
| `LGBM_Optuna_Tuning.py` | Optuna 自动调参 |
| `LGBM_MultiFold_Eval.py` | 多折时间窗口验证 |

这次拆分使生成、评估、增强模型和分析报告职责更清晰，也让后续在 Kaggle Notebook 中调参、复跑和定位错误更方便。

## 6. 第五阶段：LightGBM 候选排序模型

规则 Baseline 分数较低后，项目升级为两阶段推荐架构：

```text
多源规则召回候选商品
  -> 构造用户-商品候选训练集
  -> 使用未来 7 天购买行为打标签
  -> 构造用户、商品、交互和候选来源特征
  -> LightGBM 预测候选购买概率或排序分数
  -> 每个用户取 Top12 生成提交
```

早期 LightGBM 使用二分类方式建模，标签表示用户在验证窗口内是否购买该候选商品。模型特征包括：

- 用户活跃度、最近购买间隔、历史均价
- 商品近 7 天和近 30 天热度
- 商品购买人数、近期热度占比
- 用户-商品历史交互次数和最近交互时间
- 商品属性特征
- 候选来源标记

LightGBM 引入后，线上分数相比规则 Baseline 有明显提升，早期代表性成绩约为 Public `0.02702` / Private `0.02680`。这说明单纯人工权重排序难以充分利用候选特征，而机器学习排序模型能够显著提升 Top12 排序质量。

## 7. 第六阶段：消融实验与 SHAP 分析

项目随后围绕 LightGBM 特征做了消融实验和 SHAP 可解释性分析。消融实验发现，并不是所有看似合理的特征都有正贡献。

代表性结论包括：

1. `item_pop_ratio_30d_all` 对本地 MAP@12 提升明显，说明商品近期热度占历史热度比例能有效刻画当前流行趋势。
2. `price_diff_user_item` 没有稳定提升，说明简单价格差无法充分解释用户短期服装购买行为。
3. 部分 LightGBM gain 较高的特征，在移除后本地 MAP@12 反而上升，说明模型内部重要性不等于最终推荐指标贡献。

这一阶段形成了一个重要方法论：特征去留不能只看业务直觉，也不能只看模型 gain，而要结合时间窗口验证、消融实验、线上提交和业务解释共同判断。

## 8. 第七阶段：候选召回增强与噪声控制

在推荐系统中，候选召回决定分数上限。项目后续围绕候选召回做了多轮增强，包括：

- 属性召回：`product_type`、`garment_group`、`colour`、`section`
- 近期全局热门召回
- 商品共现召回
- 冷启动画像召回
- item-CF 相似商品召回
- product_code 变体召回
- 价格带召回
- 多天趋势召回
- department / index_group / product_group 分组召回

实验过程中发现，候选并不是越多越好。部分候选扩展本地分数较高，但线上 Public/Private 不稳定，甚至会因为新增噪声候选挤掉原有强候选导致 Private 下降。

因此项目策略从“扩大候选数量”调整为“保留强候选 + 谨慎追加稳健召回”：

1. 保留 baseline 前若干强候选。
2. 只追加少量稳定属性和趋势候选。
3. 默认关闭噪声较大的颜色、section 和邮编召回。
4. 使用 Kaggle 线上结果判断候选扩展是否真实有效。

这一阶段体现了推荐系统中候选质量比候选数量更重要。

## 9. 第八阶段：冷启动处理

H&M 数据集中有大量低活跃用户和无近期购买用户。对这类用户，仅依赖历史购买无法生成足够个性化的推荐。

项目实现了冷启动召回策略，使用用户画像分组下的近期热门商品作为兜底，主要画像包括：

- 年龄段
- 会员状态
- 新闻订阅频率
- 弱历史用户标记

冷启动增强使模型从早期 LightGBM 继续提升，代表性结果达到 Private `0.02826` / Public `0.02814`。后续实验证明，冷启动方向有效，但强度需要控制；对所有用户过度追加冷启动候选会干扰活跃用户的个性化排序。

## 10. 第九阶段：Kaggle 环境适配与内存工程

随着候选数量和特征数量增加，Kaggle 免费环境的 30GB 内存成为主要限制。项目在这一阶段进行了多项工程优化：

1. ID 映射：将超长字符串 `customer_id` 和 `article_id` 映射为 `Int32`，降低 join、groupby 和训练内存。
2. 分块预测：按用户 chunk 分批生成提交，避免一次性构建全量候选预测结果。
3. 流式提交：边预测边写出 submission，降低峰值内存占用。
4. 可配置训练规模：通过环境变量控制训练客户数、验证客户数、候选数、树数量和提交 chunk。
5. 跳过无关输出：正式提交时可跳过验证、特征重要性输出等高内存步骤。
6. LightGBM 内存控制：使用 `force_col_wise` 等配置降低训练阶段内存压力。

这些优化保证了项目在 Kaggle CPU 和 30GB 内存约束下仍能完成全量用户 Top12 推荐生成。

## 11. 第十阶段：Optuna 调参与多折验证

项目后续引入 `LGBM_Optuna_Tuning.py`，使用 Optuna 搜索 LightGBM 关键参数和部分召回参数。调参范围包括：

- learning rate
- num leaves
- max depth
- min child samples
- subsample
- colsample by tree
- L1/L2 正则
- negative sample ratio
- 候选召回数量

Optuna 帮助找到了一组较稳定的参数，例如 `learning_rate=0.028517...`、`num_leaves=64`、`max_depth=10`、`min_child_samples=80`、`n_estimators=600` 等。

与此同时，项目新增 `LGBM_MultiFold_Eval.py` 做多折时间验证，用于观察单窗口本地分数是否过拟合。后期实验发现，部分方案本地单窗口分数较高，但 Kaggle 线上提升有限，因此最终不再只依据单次本地 MAP@12 决策。

## 12. 第十一阶段：用户画像特征与召回源排名特征

后期最有效的特征方向之一是用户属性偏好特征。项目基于用户过去 90 天历史，统计用户对以下属性的偏好：

- `product_type`
- `garment_group`
- `colour`
- `section`

对应特征包括用户是否买过该属性、购买次数、属性占用户历史购买比例、最近一次购买该属性距今多久等。该方向比单纯扩展属性候选更稳定，线上成绩曾达到约 Private `0.02848` / Public `0.02872`。

另一个关键方向是召回源排名特征。早期模型只知道候选来自哪些召回源，后期进一步加入候选在各召回源内部的排名信息，例如 baseline 排名、共现排名、近期热门排名、冷启动排名和 reciprocal rank。该特征帮助模型区分“强候选”和“弱候选”，成为后续 Ranker 模型的重要输入。

## 13. 第十二阶段：Classifier、Ranker 与融合

项目最初使用 LightGBM 二分类模型预测候选商品是否会被购买。后续增加 `LGBMRanker`，使模型更贴近推荐排序任务。

两类模型各有优势：

- Classifier 对用户画像和稳定特征更敏感，线上表现较稳。
- Ranker 更关注同一用户候选集内部排序，能更好利用召回源排名特征。

因此项目后期尝试对 Classifier 和 Ranker 的提交结果进行融合。经过多组权重提交对比，当前阶段性最佳融合方案为：

| 融合方案 | Private | Public |
|:---|---:|---:|
| `ranker_source_rank 0.535 + classifier_userattr90 0.465` | 0.02881 | 0.02875 |

这是截至 2026-06-17 的当前最佳线上结果。

## 14. 阶段性结果汇总

| 阶段 | 代表方法 | Public | Private |
|:---|:---|---:|---:|
| 规则 Baseline | 多路规则召回与人工权重 | 0.01828 | 0.01841 |
| 早期 LightGBM | 候选召回 + 二分类重排 | 约 0.02702 | 约 0.02680 |
| 冷启动增强 | 画像分组热门召回 | 0.02814 | 0.02826 |
| 用户画像特征 | 90 天属性偏好特征 | 0.02872 | 0.02848 |
| Ranker/source rank | 召回源排名 + LGBMRanker | 0.02848 | 0.02855 |
| 当前最佳融合 | Ranker + Classifier 融合 | 0.02875 | 0.02881 |

从结果看，项目的主要提升来自四类工作：

1. 从规则排序升级到 LightGBM 重排。
2. 引入冷启动和用户画像特征。
3. 使用召回源排名特征增强候选质量判断。
4. 利用 Classifier 与 Ranker 的互补性进行提交融合。

## 15. 失败实验与经验总结

项目后期也经历了多次未稳定提分的实验，主要包括：

1. 盲目扩大属性召回：候选数量增加，但噪声也增加，Public/Private 不稳定。
2. 价格带召回和简单价格差特征：业务直觉合理，但没有稳定转化为 MAP@12 提升。
3. 过强分群候选：本地验证有时提升，线上泛化不稳定。
4. 扩展用户画像过多：部分 department/index_group 等特征本地较高，但线上下降。
5. 单窗口本地高分：有时无法对应线上提升，说明必须结合多折验证和 Kaggle 反馈。

这些失败实验帮助项目逐步形成更稳健的优化原则：

- 候选扩展要控制噪声。
- 特征去留必须经过消融。
- 本地验证必须按时间切分。
- 单一 Public 或单一 Local 都不能完全代表泛化效果。
- Kaggle 受限环境下，工程可运行性和模型效果同样重要。

## 16. 当前项目结论

截至目前，项目已经形成了一个较完整的电商推荐系统实践：

```text
数据理解与 EDA
  -> 规则 Baseline
  -> 时间窗口验证
  -> LightGBM 候选重排
  -> 消融与 SHAP 分析
  -> 多源召回与冷启动
  -> ID 映射和内存优化
  -> Optuna 与多折验证
  -> Classifier / Ranker 双模型
  -> 提交融合与 Kaggle 线上验证
```

项目当前最适合作为阶段性成果的表述是：

> 基于 3178 万条交易记录、137 万用户和 10.5 万商品，构建“多源召回 + LightGBM 重排”的个性化推荐系统；通过时间窗口验证、用户画像特征、召回源排名特征、冷启动处理、内存优化和 Ranker/Classifier 融合，将 Kaggle 线上成绩提升至 Private `0.02881` / Public `0.02875`。

后续如果继续冲分，优先方向包括：

1. 引入更高质量的 item embedding 或图像/文本多模态召回。
2. 构建更严格的 OOF 融合验证，减少线上试错。
3. 在更大内存环境下扩大候选召回和训练样本。
4. 对冷启动用户、活跃用户和长期未购用户分别训练或校准排序策略。
5. 将实验结果进一步结构化归档到 `experiments/`，便于答辩和后续复现。
